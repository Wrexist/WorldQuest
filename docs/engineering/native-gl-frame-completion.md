# Native GL frame completion

The iOS simulator event-only run `37137965337` received the zoom press, ran the full camera animation, and enqueued 28 frames by 17:01:29 UTC. It presented no zoom frame before the app was stopped at 17:01:35. The earlier framebuffer diagnostic inserted synchronous GL reads, limiting the animation to two submitted frames and changing the result. An `endFrameEXP` return means submission, not completed rendering.

`patches/expo-gl@16.0.10.patch` adds `GLView.waitForFrameAsync(context)` to the installed native wrapper, declarations and iOS/Android object managers. Call it after a submitted `endFrameEXP`. Its Promise resolves after the existing serial GL queue completes prior commands and `glFinish`, without waiting on JS or the UI thread and without copying pixels. This acknowledges GPU completion; it does not promise physical display scanout. iOS presentation remains driven by CADisplayLink; Android flush swaps buffers before the following acknowledgement task.

The view uses this completion boundary to limit work to one frame in flight and retain only the latest requested camera/scene. Readiness and displayed camera labels must follow completion. Geometry, textures, shader quality and Reduce Motion remain independent of this queue limit.

The iOS implementation checks atomic background/destruction state before touching EAGL, including after the task reaches the GL queue. It bypasses the general `runAsync` helper because that helper touches GL even when a callback returns early. Context destruction invalidates pending completion callbacks. Android removes and rejects pending Promises before shutting down its GL thread; callbacks already running cannot settle them twice. An active GL failure rejects rather than reporting successful completion.

The patch is pinned through pnpm. Android autolinking explicitly builds `expo-gl` from source so a prebuilt AAR cannot silently omit the method. A new native binary is required; old or unpatched native modules reject with the wrapper's availability error. Do not replace this boundary with per-frame `getError`, `flushEXP`, a snapshot, a timer, or an unbounded fallback: those respectively block JS, copy pixels, or fail to measure completion.

`scripts/expo-gl-frame-ack.test.cjs` exercises the actual installed JS wrapper and compiles the actual extracted Java acknowledgement/cleanup methods against controlled GL and Promise boundaries. The Promise boundary includes Expo's actual overload signatures: Android compilation in run `37140772660` caught an ambiguous untyped `resolve(null)`, now explicitly cast to `Object`, and the expanded harness reproduces that failure before the fix. Its six Java lifecycle cases cover success, destruction before/during a frame, requests after destruction, GL failure and multiple pending Promises. The Java test skips only when no JDK is available. Full native compilation and an uninstrumented zoom/pixel acceptance run remain required to validate the integration; local wrapper/lifecycle tests do not establish native pixels or physical-device performance.
