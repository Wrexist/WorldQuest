## Method, and one thing it nearly got wrong

Every claim below is a grep or a file read, quoted. Worth recording how close this came
to reporting a false blocker: the first RLS check used an uppercase pattern and returned
**zero** tables with row-level security, then a corrected pattern returned **7 of 13** —
six tables apparently unprotected, which would have been the most severe finding
available. Both were wrong. The migrations column-align their SQL:

```sql
alter table lessons    enable row level security;
alter table xp_ledger   enable row level security;
```

`[a-z_]+ enable` does not match `lessons    enable`. All 13 tables are covered. A
security finding that would have sent someone hunting a non-existent hole is its own kind
of harm, so: read the statements, do not trust the summary count.

## What holds

**RLS is on every table.** 13 tables created, 13 `enable row level security` statements,
13 policies. No table is created without one.

| | |
|---|---|
| Covered | `profiles` `entitlements` `user_facts` `review_log` `lessons` `xp_ledger` `coin_ledger` `wallets` `inventory` `streaks` `subscriptions` `subscription_events` `shop_items` |

**No service-role key can reach the client.** `packages/api/src/client.ts:48` rejects a
config whose publishable key contains `service_role`, and the test at
`client.test.ts:62` feeds it both a `sb_secret_` and a `service_role` JWT. The check is
in the constructor path rather than in a lint rule, so a misconfigured deploy fails at
startup instead of shipping a key that can read every user's rows.

**Rewards are server-decided.** XP, coins, mastery and streaks are written by
`record_lesson`, the mastery trigger and `purchase_item`. Submission time is validated
server-side (`_shared/submission-time.ts`) rather than trusted from the client, which is
what closes the "answer instantly, mint mastery" path. `hearts_lost` is the one
client-reported field and is treated as a statistic — nothing is paid or withheld on it,
which is what makes trusting it acceptable.

**Crash reports cannot carry free text — by type, not by discipline.**
`apps/mobile/src/lib/reporting.ts` defines `CrashReport` with no field that can hold a
message: every field is a fixed union or a constrained identifier. A React error string
routinely contains a prop value, and in this app a prop value can be text a child typed
into the collection search. A sink physically cannot forward a message it was never
given. This is the right shape for a guarantee nobody will remember to re-check.

**Analytics treats unknown as a child.** `lib/analytics.ts:42` — `if (isChildAccount !==
false) return`. Null is not permission. That ordering matters because the age answer is
not stored until the end of onboarding, so every event before it is suppressed rather
than attributed.

**No real secret is committed *in the reviewed files*.** Scoped deliberately: the method
here is grep and file reads over the working tree, which does not cover git history, build
artefacts, or low-entropy credentials that no entropy heuristic would flag. No secret
scanner (gitleaks, trufflehog, or similar) has been run against this repository, and until
one has, the honest claim is about the paths reviewed rather than about the repository.
Within that scope the only high-entropy blobs are
`supabase/functions/_src/_shared/__fixtures__/jws.json` — App Store notification
fixtures signed by a synthetic chain whose CNs decode to "WorldQuest Test
Root/Intermediate/Leaf", with bundles `com.worldquest.app` and `com.attacker.app`. They
exist to test signature *rejection* and are generated by
`scripts/make-jws-fixtures.cjs`.

**Third-party SDKs are two, and one is inert by default.** `@sentry/react-native` (no
DSN → no-op, routes to console) and Expo's own modules. There is no ad SDK, no attribution
SDK, no session-replay SDK. `NSPrivacyTracking: false` and an empty
`NSPrivacyCollectedDataTypes` are consistent with that.

## Findings

### ⚠️ 1 · `en-XA` is now reachable in a production bundle

This review's own session added `globalThis.__wqEnablePseudoLocale` and a
`__WQ_PSEUDO__` override so the screenshot harness could produce the pseudo-locale
screenshots the Definition of Done asks for. That is a deliberate, documented widening of
what a production bundle exposes.

**Why it is not a blocker.** The function refuses unless `__WQ_PSEUDO__ === true`, which
nothing in the app sets; `en-XA` is not in `SUPPORTED_LOCALES`; and the Settings picker
reads `LANGUAGE_CHOICES` rather than the loaded bundles, so a forced pseudo-locale cannot
appear as an option. The worst case is a user who runs JavaScript in their own app
process changing the language of their own copy of the app.

**What to weigh anyway.** It is a global on a shipped bundle. If the reviewer's line is
"no test seam ships", the alternative is a separate non-production export target for the
harness, which is more machinery than the risk justifies today. Recorded so the decision
is visible rather than discovered.

### ⚠️ 2 · Sentry's round trip has never happened

`Sentry.init` only runs with `EXPO_PUBLIC_SENTRY_DSN` set, and no DSN exists in any
environment reachable from here. So the PII-free property above is proven by the type
system and **not** by observing a single event. The first real DSN is the first time
anyone learns whether the transport works at all.

This is item 4 on the release checklist wearing a different hat: no beta, no crash-free
number, no evidence the reporting path functions end to end. It belongs in the device
pass, not in code review.

## Could not be verified here, and must not be recorded as passing

| Property | Why not |
|---|---|
| RLS actually denies cross-user reads at runtime | `supabase/tests/rls.test.sql` runs in the `database` CI job and is green, which is real evidence — but it runs against a local stack, not the production project. Nobody has attempted a cross-account read on the deployed database. |
| The privacy manifest matches what is actually sent | Requires watching real traffic from a real build. The declaration is *consistent with* the two SDKs present; "matches reality exactly" is a claim about bytes on a wire. |
| Child accounts stay silent on a device | The no-op is unit-tested. Whether a child build emits nothing needs a device and a proxy. |

## Recommendations, in order

1. **Before any beta:** set a Sentry DSN in a staging build and confirm one event
   arrives with no message field. That closes finding 2 and unblocks the crash-free
   measurement the release checklist wants.
2. **Before submission:** run the RLS suite against the deployed project, not only
   locally — using **two dedicated test accounts holding synthetic data**, or a staging
   project. Not two production accounts: a cross-user authorisation test is by
   construction an attempt to read someone else's rows, and doing that against a real
   person's data to prove they are protected is the wrong trade even when it succeeds.
3. **Decide on finding 1** — ship the harness seam, or build a separate export target.
   Either is defensible; leaving it undecided is not.

Reviewed by an automated pass over source and schema. A human should re-read findings 1
and 2 before submission, because both are judgement calls about acceptable exposure
rather than facts about the code.
